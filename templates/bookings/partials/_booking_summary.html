{% comment %} The booking summary — the *right* grid child of `.wrap.booking`. Included directly by booking.html for both the full page and any htmx response to this same BookingPage URL (see _booking_panel_form.html's own comment for why: BookingPage has no htmx-aware view, so htmx always receives the full page and `hx-select`s just #booking-panel out of it). This aside's own `hx-swap-oob="true"` is what lets it refresh anyway: htmx finds it by id anywhere in that same full response and swaps it in out-of-band, independently of whatever the triggering control's `hx-select` grabbed for the main target — so a day/time/reading change updates the price and "Continue to payment" state together with the left column from a single request, with no extra attribute needed on the controls themselves. Context (apps.bookings view): summary {reading_label, price, date_label, time_label, ready, reading_slug, day_iso, slot_value} — `time_label` already has its zone abbreviation baked in (e.g. "9:00 am NZST" — see apps.bookings.availability's own `time_label` construction), so it is not repeated here; partials/_booking_panel_form.html's Step 2 sub-text names the zone again next to the slot picker itself, before a time is chosen hold_minutes how long a chosen slot is held before it's released The Pay control: a real `
` with hidden `reading`/`slot`/`tz` fields — `reading` and `slot` come straight from `summary` (the reading/day/slot already chosen in steps 1-2); `tz` starts empty and is filled in by a small progressive-enhancement script in booking.html (`data-tz-field` is its hook) using `Intl.DateTimeFormat().resolvedOptions().timeZone` — with no JS it stays empty and `apps.bookings.availability.resolve_timezone` falls back to Leslie's own timezone server-side, never a guess made up here. No-JS path: a plain POST navigates to whatever `bookings:checkout` returns — a redirect to Stripe Checkout on success, or the whole booking page re-rendered with `checkout_error` set on failure (FINDING 1, reviews/2026-09-22-final-build-review.md — a plain POST used to get back `_checkout_error.html` on its own, with no page chrome at all; now `apps.bookings.views._checkout_error` re-renders this same page, and `checkout_error` below is how that message actually reaches this region on that full-page render). With htmx, the same POST instead swaps `#checkout-error` in place (success still redirects, via `HX-Redirect` — htmx follows that header as a full navigation regardless of `hx-target`) so a failed attempt never disturbs the reading/day/time already chosen alongside it — same message, same `.form.invalid > .err` reveal rule (static/css/_components.css), whichever path rendered it. {% endcomment %}
